# Organization invitations

Invitations are optional and disabled by default. `ORG_INVITATIONS_ENABLED=1` enables issuance, authenticated preview and acceptance when valid TLS SMTP delivery is configured through the existing `RECOVERY_SMTP_*` fields. This flag is independent of password recovery and email verification. Enabled invalid configuration prevents startup. No live mail destination has been activated or validated during development.

A browser-session organization administrator can send invitations from organization settings. The administrator chooses an email address and a fixed organization role; the account may register after issuance. Existing members must use ordinary membership management for role changes. Delivery goes to the specified email and a server-configured frontend link, never a user-supplied callback URL. The issuing account has a ten-attempt send budget per fifteen-minute window. Mail transport shares the three process-local delivery slots and verified TLS socket controls. Delivery failure marks the invitation failed and prevents acceptance; there is no durable mail queue or delivery retry guarantee.

Only a SHA-256 hash of a random 256-bit token is stored. Links use a fragment that the client removes from the address bar. The recipient signs in or registers normally with the exact invited email, including existing MFA requirements. A private authenticated preview shows the organization name, initial role and expiry; accepting requires a separate explicit action with normal Origin and CSRF protection. A link never creates a session or automatically joins an organization. API tokens cannot manage, preview or accept invitations.

Invitations expire after seven days, are atomically claimed once, and require the issuing administrator to remain active in the same administrator membership with the same credential version. Role loss, membership removal/re-addition, account disablement or credential rotation invalidates outstanding authority. Revocation and acceptance coordinate under the existing single-worker membership lock. A recipient's current account/email/credential version is rechecked before membership changes. Existing membership roles and memberships in other organizations are never overwritten. Old API credentials do not regain validity when a removed member rejoins with a new membership ID.

Administrators can search and page the complete invitation register, filter status and revoke pending links. Token hashes and issuer credentials are omitted. The expiry TTL removes invitation metadata after seven days; organization/account audit events remain separate records. Revocation works even when mail is disabled. Issuance, preview and acceptance are blocked when invitations are disabled.

The application still requires one API worker. Claiming an invitation, inserting membership and recording status/audit are separate database writes rather than a transaction. An interrupted or ambiguous write can leave an `accepting` record or an already-created membership with an error response. The token cannot be replayed to overwrite a role. Reload account membership and ask an administrator to review before creating a replacement invitation. Distributed coordination, durable mail delivery and production delivery acceptance remain operational work. Invitation acceptance does not independently mark the email verified or change the sign-in policy.
