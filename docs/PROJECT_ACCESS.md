# Membership project access

Organization administrators can choose **All current and future projects** or **Selected projects only** for each non-administrator membership. Use the Project access action in the member register or POST `/api/members/{user_id}/project-access` with `mode` (`all` or `selected`) and `project_ids`. Selected access supports up to 500 distinct project IDs in the same organization; an empty selection grants no project data. Normal organization roles still determine which actions are available inside accessible projects. This does not add custom roles or per-project role overrides.

Existing memberships and new grants/invitations retain all-project access until explicitly restricted. Organization administrators always retain all-project access so they can manage grants and preserve administration. Promoting an account to organization administrator clears an earlier restriction; demoting it does not automatically restore old restrictions. Configure its project policy explicitly after demotion. Invalid stored policy fails closed for non-administrators; absence of the field preserves legacy all-project behavior.

Grant changes require a browser session, trusted Origin/CSRF and fresh administrator membership/account/credential authority. Selection validation rejects unavailable/cross-organization projects. The write compares the target membership identity, role and old policy; it shares the supported single-worker membership lock with role changes and removals. It does not create accounts, change roles, enroll MFA or rotate account credentials. Removal/rejoining creates a fresh membership and retains existing token lifetime guards.

Every subsequent request reloads current membership policy. Existing API tokens inherit the owner's current role and project access; changing that access immediately narrows or broadens their project visibility. Tokens do not have an independent fixed project selection yet. They still cannot enter account/membership administration. Restricted security leads cannot configure organization-wide webhooks or change organization SLA policy; those operations require all-project access. Restricted members cannot create projects or shared project templates. Organization directory metadata, shared project templates and SLA reads remain organization metadata available to members; another member's project grant IDs are shown only to administrators and the member themselves.

The shared repository combines caller filters with project admission using an independent AND predicate. It scopes project pages, complete registers, workspace previews, aggregates/counts, findings, tasks, assessments, scanner/import/inventory records, AI sessions and report/evidence metadata. Existing report/evidence child blobs without project IDs are read only after checking their authoritative parent. New child records carry project attribution. Project identity and blob parent links cannot be changed through repository updates.

Audit events with a resolvable project resource receive project attribution. Restricted members see only events attributed to their accessible projects; older unattributed events and organization-wide account/membership events are omitted. There is no heuristic backfill of historical events. Events are still an application ledger, not tamper-proof storage. Aggregate counts cover only accessible projects and may change between queries.

Queued checks recheck current project and membership identity before execution. Requests/checks already running may finish using their admitted context; this is not immediate cancellation or durable worker ownership. Access changes cannot recall previously downloaded or browser-cached data. Reload the workspace to refresh the displayed policy and available projects. Cross-worker membership coordination remains required before multiworker deployment.

Synthetic tests exercise browser and pre-existing API-token restrictions, hidden-project reads/mutations/bulk operations, aggregates/search/workspace/audit, legacy evidence/PDF/snapshot downloads, report/export rejection, administrator protection, empty selection and all-project restoration. No real memberships or permissions are changed during acceptance.
