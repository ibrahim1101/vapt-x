# Custom roles and service identities: design boundaries

Current authorization combines organization membership, a built-in or organization-defined role, current project admission and (for bearer credentials) token action scopes plus membership identity/credential epoch. Membership project selection and optional immutable project caps for human API tokens are implemented. Custom roles and organization-owned service identities are implemented as distinct principal types.

Custom roles use immutable UUID identifiers with an explicit allowlist of existing action permissions. Read is required; administrator, member-management, scope-authorization, integration-management and wildcard permissions are excluded. Only a live built-in organization administrator can create, edit or delete roles. Updates use expected-version compare-and-swap, apply on the next request, and cannot delete an assigned role. Role assignment remains organization-scoped, is versioned and auditable, and custom permissions intersect bearer-token scopes and current project admission. Custom-role APIs are not exposed to bearer credentials. Negative tests cover tenant boundaries, forbidden permissions, live policy changes, project writes, token-scope intersection, assignment and queued scan admission. Coordination currently follows the supported single-worker process-local membership lock; durable coordination is still needed before multiworker deployment.

Service identities are organization-owned principals, separate from human account passwords, MFA and recovery. Each credential has immutable action and project caps, expiry, one-time secret display/hash-only storage, explicit human ownership, rotation/revocation and last-use metadata without raw secrets. Every request intersects credential caps with the identity’s current grants and projects. If the named owner loses organization membership or is disabled, credentials fail closed; an administrator must explicitly transfer ownership before the principal works again. Human API tokens remain tied to a human membership and are not service identities.

Service bearer credentials are restricted to the existing domain API family allowlist. They cannot access account, membership, credential or service-identity administration. Queued scans revalidate credential revocation/expiry, current identity grants, project intersection and the current explicit owner before starting. Project admission uses the same repository boundary as other principals. A running request may finish unless an execution-specific cancellation boundary is added.

Membership and service-identity coordination currently use process-local locks; multiworker operation remains unsupported. Operational release/restore acceptance is separate. Tests do not establish production readiness or exhaustive security coverage.
