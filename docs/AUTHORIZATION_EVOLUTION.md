# Custom roles and service identities: design boundaries

Current authorization combines organization membership, a built-in or organization-defined role, current project admission and (for bearer credentials) token action scopes plus membership identity/credential epoch. Membership project selection and optional immutable project caps for human API tokens are implemented. Custom roles are now implemented for browser-managed human memberships. Independent service identities remain unimplemented.

Custom roles use immutable UUID identifiers with an explicit allowlist of existing action permissions. Read is required; administrator, member-management, scope-authorization, integration-management and wildcard permissions are excluded. Only a live built-in organization administrator can create, edit or delete roles. Updates use expected-version compare-and-swap, apply on the next request, and cannot delete an assigned role. Role assignment remains organization-scoped, is versioned and auditable, and custom permissions intersect bearer-token scopes and current project admission. Custom-role APIs are not exposed to bearer credentials. Negative tests cover tenant boundaries, forbidden permissions, live policy changes, project writes, token-scope intersection, assignment and queued scan admission. Coordination currently follows the supported single-worker process-local membership lock; durable coordination is still needed before multiworker deployment.

Service identities should be organization-owned principals, separate from human account passwords, MFA and recovery. Each credential should have immutable action and project caps, expiry, one-time secret display/hash-only storage, explicit administrator ownership, rotation/revocation and last-use metadata without raw secrets. A human owner losing membership must not silently transfer authority; define administrator handoff and orphan disablement before provisioning. Human API tokens intersect optional fixed project caps with live human membership and are not service identities.

Before broadening token access, intersect credential caps with current principal grants on every request, enforce the same repository project boundary, and reject all account/membership/credential administration families. Define whether archived/deleted projects invalidate grants, and test removed/rejoined memberships, stale policy versions, concurrent revoke/mint, tenant isolation and queued jobs. A running request may finish unless an execution-specific cancellation boundary is added.

Service-identity requirements remain future work, not available product controls. The supported deployment remains one API worker, and operational release/restore acceptance remains separate. Custom-role tests do not establish production readiness or exhaustive security coverage.
